# HarborCache performance and user-needs review

Reviewed 21 October 2026. HarborCache baseline: 1.2.6, commit `6d235793ec8ad5bcbd9885b35c8043d6915fcea9`. This is a source review and implementation plan, not a new performance release. The 1.2.6 ZIP is unchanged.

## What the evidence supports

The final 1.2.6 acceptance run passed all ten jobs. Its seven-round comparison used native PhpRedis for all three engines. HarborCache consumed 242.149 ms PHP CPU for the measured operation workload, compared with 234.553 ms for 1.2.5 and 199.183 ms for Redis Object Cache 3.0.0. Peak PHP allocation was 36, 36 and 34 MiB respectively. These are workload totals, not server CPU percentages.

HarborCache is about 21.6% above the free plugin's PHP CPU in this test. Matching that result would require reducing HarborCache's current CPU time by about 17.7%; getting within 5% would require about 13.6%. Those are targets, not demonstrated gains.

The gap varies by operation: 1,000 memory reads take 0.551 versus 0.415 ms, 20 forced Redis reads take 2.395 versus 2.297 ms, and a 100-key bulk read takes 0.490 versus 0.413 ms. Large-value pairs take 0.296 versus 0.257 ms. Optimizing the largest percentage gap alone would not establish the largest real-site benefit.

HarborCache retains a useful invalidation trade-off: invalidating 5,000 seeded entries takes 0.335 ms and two commands, versus 8.022 ms and about 5,723 commands for the free plugin's tested group flush. HarborCache leaves old generations to expire or be reclaimed. This is not immediate memory reclamation, and the benefit already existed in 1.2.5.

Evidence: [final CI run](https://github.com/shahidirfan100/harborcache/actions/runs/39572042761), its `linux-performance-applications` artifact, and `VALIDATION-1.2.6.md`. This review reuses those measurements; it does not claim a new Redis benchmark or profiler trace.

This is a targeted sample of public reports, not a survey. The fetched WordPress.org review page showed 4.5/5 from 179 reviews, including 149 five-star reviews. It would be misleading to describe the community as generally tired of the plugin. The opportunity is to serve particular deployments better.

## What should distinguish HarborCache

Target site owners who need shared-Redis isolation, reliable maintenance/recovery, understandable diagnostics and low collection overhead. Those are specific needs supported by the reports. A larger options page does not make the product a better alternative.

Three original product proposals follow from those needs:

1. A local cache-benefit report: measure connect time, Redis time, PHP cache work and payload volume separately. Offer controlled staging comparisons against no persistent cache; never disable production caching automatically to collect a comparison. Display the sample window, configuration and limits beside the result.
2. A namespace safety check: explain the active owner, supported invalidation mode, required ACL capabilities and expected old-generation retention. Probe only temporary keys inside the installation's own namespace. Never test by deleting another tenant's keys or exposing their names.
3. A maintenance recovery check: verify that a changed/restarted endpoint reconnects with the intended database, credentials and TLS policy. Keep ordinary traffic inexpensive; run diagnostics on explicit request or bounded sampling. Any future cross-request circuit breaker must fence missed invalidations before old Redis data can be reused.

Do not add public REST routes, cloud accounts, automatic server tuning, synthetic testimonials or claims of being fastest. Preserve the current dashboard colors and widget. Improve its explanations only when a measured state or real action needs to be shown. Preserve existing GPL attribution and licenses; original additions do not erase inherited code provenance.
